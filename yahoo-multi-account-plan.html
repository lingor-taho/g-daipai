00本地实现与操作说明

2026-10-10：已实现可配置账号列表、插件绑定、按账号执行、商品账号名额、逐级黑名单转交、成交账号订单流程、独立提醒与导入。本地使用临时数据库和模拟 Yahoo 数据测试；没有部署或执行真实竞拍、付款。

启用方法

  1. 先关闭旧插件及其正在执行的页面，核对 Yahoo 已提交结果，停止 API 后备份生产数据库。更新 API、后台、用户端静态文件、共享模块与完整 yahoo-plugin，重启 API、reload 插件。
  2. 先只保留当前 A：首次迁移空账号数据归 A，旧配置中的运行状态复制到 A。首次有存量任务的迁移自动额外保存数据库副本；旧 processing 任务标记“结果未确认”，不会直接重新出价。正常任务／订单 ID、金额、用户与已入表事实保留。
  3. 后台「账号管理 → Yahoo 执行账号」设置主账号、备用顺序、启用状态、Yahoo ID、Gmail 和 Chrome profile。绑定码仅在管理员后台显示；同一个 Yahoo ID 或 profile 不能重复注册。
  4. 仅一个账号且插件未绑定时，插件自动绑定该账号；配置多个账号后，在各 profile 的扩展详情 → 扩展选项填写对应账号 ID 和绑定码。先人工核对本 profile 的真实 Yahoo / Gmail 身份，避免把正确绑定码填入错误 profile。系统按绑定号和实例隔离工作，当前不自动读取真实 Yahoo ID 来核实身份。
  5. 后台同时显示每个插件在线状态及其 Yahoo 登录／验证回报、flag、计数与提醒。插件重载后旧实例心跳可能保持在线最多 45 秒，新实例随后恢复连接。只配置 A 时先验收原业务，再逐个增加备用；不增加账号也可使用新执行架构。
  6. “出价并发任务数”是各插件独立上限。值为 2、三个插件时总计可以并发 6 件；配置仍共用。窗口截图／PIN 输入单独排队，PIN 不阻止任务提交。

异常处理

原业务规则以开发前提交 9d22b23 为基线。付款出问题仍立即中断本轮后续付款并关闭付款 flag，管理员按原入口继续后才恢复；归还尚未执行的领取标记不等于自动继续付款。多账号改造及修复只增加账号区分和领取校验，不调整原扫描判断、出价策略或其他既有业务规则。

  • 明确卖家黑名单、确认本次拒绝且无有效或未知旧入札，才转交原任务；其他未知错误不会盲目转交。后台任务页显示结果待核对，关闭该账号插件、核实无入札后才能解除保护，再按原归属重新提交。
  • 订单工作领取后插件中断或返回丢失，不自动重新领取。后台显示待核对工作；先关闭原插件，核对成交账号实际状态，付款已成功时先同步真实状态，再确认释放领取。已有订单始终使用成交账号，不改绑主账号。
  • 取消任务仍保留商品账号归属；黑名单安全转交会释放已明确拒绝的原位置。同捆不跨账号；导入批次创建时选定读取 Yahoo 号，确认导入继承来源号。
  • 公共拍卖历史只有一份全局队列；落札商品只由成交账号读取，未落札从参与该商品的在线账号按顺序选一个，账号切换不重置三次失败上限。

01最终范围与业务规则

本版替代 1.0 的双账号限制及“同商品只接受一个用户”规则。最新需求是一个主账号＋可增加的备用账号列表；同商品可由不同 Yahoo 账号分别替不同用户竞拍。

主 → 备用1 → …

按优先级分配。明确可转交的失败继续向后寻找可用账号，全部不可用才终止，不循环。

商品＋账号 · 一个用户

同商品可有多个用户，每人占一个 Yahoo 账号；同账号可承接多个不同商品。

先完成单账号迁移

第一阶段只有当前 A，不新增备用账号、不启用转交，基础结构直接支持多账号。

1.1 已确认的最终需求

  1. 后台配置一个主账号＋备用1、备用2、备用3等多个备用账号，不把数量固定为两个。各 Yahoo 账号登录独立 Chrome profile及对应 Gmail，同一套插件分别绑定固定账号 ID。
  2. 当前 A 为主账号，备用列表可增加、排序和设置启用状态。名称与主备用角色可调整，固定账号 ID 不变，历史数据不随排序改绑。
  3. 新需求优先选择主账号；该商品已被主账号替其他用户承接时，按顺序选择备用账号。同一商品在同一个 Yahoo 账号下只归一个用户；不同商品互不占用名额。
  4. 同商品存在几个可分配的在线账号，就最多接受几个不同用户；账号全部占满或剩余账号均离线时，直接返回提交失败及原因，不预留离线名额、不建立等待账号恢复的新任务。
  5. 离线账号跳过。在线账号需要 PIN 验证时仍可接受任务，PIN 不作为跳过账号或提交失败的条件；其他登录／验证场景沿用目前程序的实际暂停边界，不新增“所有验证都禁止提交”的规则。
  6. 当前执行账号被卖家明确拉黑等安全条件满足时，原任务按顺序寻找该商品未被其他用户占用、在线且未尝试过的后续账号。备用1同样明确失败时继续找备用2等，全部可用候选耗尽才终止，不返回已尝试账号或循环。
  7. 同用户对同商品后续调整最高价、再入札和自动 followup 沿用原校验与已有归属，不为同一个用户额外占用多个账号；转交后继承新执行账号。
  8. 任务、入札、落札、订单与金额统计合并展示；相关明细增加“执行 Yahoo 号”，用户端仍遵守原用户权限隔离。
  9. 实际落札账号承担该订单后续交易、同捆、消息、付款、物流扫描及确认收货，不能交回另一账号操作。
  10. 后台系统配置继续只有一套；各账号独立保存运行状态、flag、计数、验证问题和错误。“出价并发任务数”保持为每个插件的上限，所有插件读取同一个配置值，不改为服务器总上限。
  11. 所有账号的邮箱验证、文字验证码和 PIN 问题可以同时显示，各提醒、输入与继续按钮只作用于对应账号。需要全机键盘／前台焦点的动作排队执行。
  12. 个人任务与入札状态按自己的执行账号查询。公共拍卖历史仍按商品保存一份；落札优先使用成交账号。未落札多账号商品的采集选择方案见 3.2，不要求每个用户重复采集。
  13. 批量任务建立成功后，账号转交是原任务的后续执行，不再次显示“批量提交失败”。执行最终失败在原任务列表展示；任务未建立的商品显示提交失败。
  14. 停止系统任务不等于撤销 Yahoo 已接受的入札；仍有有效入札或结果未知时，不能立即释放对应“商品＋账号”的用户归属。
名额针对商品，账号不是被整个人独占

A 拍商品 X，不妨碍 A 同时替其他用户拍商品 Y。只有“同一个商品＋同一个 Yahoo 账号”不能同时归不同用户。此前“一个商品只出一个价／只接受第一个用户”的表述已被本次修正替代；原有同用户加价、定时和低价分步能力继续保留。

1.2 新提交的账号分配

候选账号情况新需求的处理
在线、该商品名额未占用可分配，按主账号与备用优先级选择；同用户已有归属时沿用原关联。
在线、需要 PIN仍可接受任务。PIN 对付款等具体操作的影响沿用原程序，不阻断任务提交。
离线跳过，继续寻找其他账号。不为新需求预留该账号，不排队等待它上线。
替其他用户承接了同商品跳过这个“商品＋账号”位置，不能抢占；账号承接其他商品不影响此次分配。
所有位置占用／剩余位置离线返回提交失败，区分“账号名额已占满”与“剩余账号离线，暂无可用账号”。

身份不匹配、未知绑定或停用新分配的账号不能进入候选。插件在线与 Yahoo 登录状态分开显示，心跳判离线阈值在开发审计中确定，不能让旧的在线标识无限期有效。

1.3 转交条件与终止条件

触发情况处理规则
当前账号被卖家拉黑当前唯一自动转交条件。使用明确错误码；确认本次被拒绝、没有有效或未知的旧入札，结束本次执行，再原子预留后续账号并转交。
其他“不能执行”保留扩展方向，但不直接用所有 failed 触发。每个新增条件先定义明确证据、结果核实方法及独立回归；第一阶段和首次转交版本均不扩大。
我们把卖家拉黑与卖家把 A 拉黑区分，默认不自动绕过；当前解析把两种方向归为同类，需拆分原因。
断网、超时、页面异常、登录验证不直接换账号。先等待原账号恢复或核实 Yahoo 结果；无法确认时保留等待核实，不盲目重放。
价格超过上限／商品已结束按原业务规则结束，不因换账号提高上限或继续出价；保留既有自动延长结束时间的页面核实机制。
备用账号同样明确被拉黑继续向后寻找未占用、在线且未尝试的候选，不回到失败账号；没有候选时终止执行并记录尝试轨迹。
后续账号占用了同商品／离线跳过，不挤掉其他用户、不等待离线名额。若只是承接其他商品，可以继续使用。
所有后续候选耗尽按执行失败收尾，给出无可转交账号及各尝试原因，和人工 cancelled 区分；新增账号后不自动复活已终止任务。
已接受任务之后账号掉线与“新提交找不到在线账号”区分。建议保留原任务归属并提示中断，恢复后核实结果与时效；不能仅因掉线盲目换账号或释放名额。
失败后实际落札Yahoo /my/won 仍是事实来源；按成交账号校正 failed/processing/bidding 等任务并生成订单，人工 cancelled 的既有边界不自动改变。

1.4 通俗示例

主账号＋两个在线备用账号结果
user1 提交商品 X分配主账号 A。
user2 提交商品 X分配备用1。
user3 提交商品 X分配备用2。
user4 提交商品 X失败：该商品的在线账号名额全部占用。
备用2离线，user3新提交失败：剩余账号离线，不占位等待。
备用2在线但需要 PIN，user3新提交允许提交，分配备用2。

同商品转交：user1 用 A 拍 X，user2 用备用1拍 X。A 被拉黑后，user1只能找备用2等剩余位置；不能抢 user2的位置。

不同商品转交：user1 用 A 拍 X，user2 用备用1拍 Y。A 被拉黑后，user1可以转备用1继续拍 X，不影响 Y；X、Y的名额分别计算。

批量提交：10件已建立任务，其中1件由 A 转备用1，再转备用2，始终是同一件已提交任务。所有候选失败时在任务列表显示执行失败；商品校验、账号名额等导致任务未建立时，才在批量结束反馈提交失败。

多人竞拍：不同用户分别使用不同 Yahoo 账号参与同商品，可能相互竞价。各自最高价、是否领先及最终落札独立判断，提交成功不保证落札，也不能把其他用户的最高价公开给当前用户。

02账号管理与后台呈现

2.1 Yahoo 执行账号管理

增加独立“Yahoo 执行账号”页面，支持一个主账号和可增加、排序的多个备用账号。现有用户与服务器管理员账号页面保留；数据库已有 yahoo_accounts 可作为扩展基础。第一阶段只启用现有 A。

信息要求
固定账号 ID、名称供任务、日志、订单、验证引用。名称可修改，账号 ID 不随主备用切换改变。
主／备用角色与顺序一个主账号、多个备用账号。可增加、排序并控制是否接受新分配；角色调整不改绑存量任务和订单。第一阶段仅 A。
预期 Yahoo ID显示预期 Yahoo ID、profile、Gmail 及该插件回报的登录／验证状态；实际身份由管理员在 profile 中核对，当前没有自动读取真实 Yahoo ID 的检测器。发现不一致先停插件纠正绑定。
Chrome profile、Gmail保存 profile 标识及预期验证码邮箱。profile 内插件显式绑定账号，不能仅凭目录文字或窗口标题猜账号。

登录与验证状态正常、需要登录、邮箱验证、文字验证码、PIN、未知；包含最近确认时间，旧的“正常”不能无限期保持。

2.5 多窗口问题的通俗说明

  1. 每个插件分别跑任务：配置“出价并发任务数”为2，三个插件各自可同时跑2个，合计最多6个。电脑变慢时由管理员人工调整统一配置；系统不自动降低并发，也不新增服务器总出价上限。
  2. 输入 PIN 不抢窗口：A和备用1都需输入时，先找到 A 的正确窗口完成，再处理备用1，避免输入到另一个账号。排队只保护需要抢前台焦点的动作，不把出价并发改成全机共享上限，也不影响任务提交。
  3. 提醒分别处理：A需要 PIN、备用1离线、备用2需要邮箱验证，可以同时显示；处理完 A，只清除 A 提醒，其他问题继续保留。

03全流程账号归属

STEP 1提交与分配

按顺序寻找在线的商品账号名额，原子预留并建任务；同用户复用归属，无名额直接失败。

STEP 2执行与同步

凭账号与领取标识执行，明确安全条件下向后转交；各用户／账号状态独立，后台汇总展示。

STEP 3落札与订单

按实际成交账号＋商品归属确认用户，订单后续交易、付款与物流固定使用成交账号。

功能最终要求
单条／批量提交共用商品账号名额分配入口与请求去重。批量入队不代表每件已拿到账号；准备完成、正式建任务时检查在线候选并预留，无名额则该行提交失败。建议按成功预留并建任务的顺序确定先后。
定时／多次／低价分步原最高价、税口径、策略和结束时间校验保持不变；followup 继承用户、账号和原提交关系。转交不增加新的用户提交次数。
入札同步按账号＋商品记录。完整同步只让本账号旧记录过期；同步异常不能当空列表清除。最高价身份和已出价金额属于账号，商品当前价仍是共享快照。
落札同步按实际成交账号＋商品＋对应用户归属匹配，不能按该商品最新任务猜用户。仅该账号对应用户获得成交事实；其他用户的任务分别收尾。发现归属矛盾或不同账号成交冲突时提示，不覆盖订单。
交易／同捆订单账号过滤所有领取与回写；同捆主子商品必须同 Yahoo 账号，人工普通同捆修复、商城同捆补录同样校验。原暂停 24 小时边界保留。
付款／扫描／收货按成交账号执行。混合账号订单选择由 API 分派；每账号保留进度、待办和错误。一个账号出错不结束另一账号工作；发送支付结果未知不自动重付。
Yahoo 消息跟随订单账号，原独立消息线、同订单读发互斥及发送未知不自动重发规则保留；消息页归属与清理仍按当前实例隔离。
拍卖记录公共历史按商品一份 HTML／JSON，采集选择见 3.2。领取关联账号并校验商品级租约，保留过期、三次失败、迟到回写和批次规则，不随账号数复制队列。
失败分析／小图表读取当前用户的任务与对应账号状态，其他用户仍在入札／已落札不能误隐藏自己的失败分析。转交不增加三角；保留取消排除、followup 合并和时区。个人提交最高价不混入其他用户。
90 天统计／CSV各账号后台统一汇总，当前用户统计范围不变。三个用户同商品是三个用户任务、一个公共商品；转交不增加任务。落札数按实际订单，收获分母按当前用户当日到期商品去重；CSV 标明执行账号。
Google 表格配置与服务端凭据共用，profile 的 Gmail 不参与表格认证。保留逐商品查重、已有数据成功处理、同捆只补缺项；增加账号信息须兼容现有列、颜色、备注和收货读取。
批处理／数据清理重同步、重扫单号、订单状态调整、订单用户修改都保留账号事实；删除一个账号的任务不能误删其他账号有效入札或共享商品。商品整体删除应清楚显示范围。

3.1 订单导入

当前每次明确选择一个目标 Yahoo 账号，默认主账号。批次创建时固定 account_id，只由该账号 profile 读取 /my/won；候选行、确认导入的任务与订单均继承来源账号。现有按系统用户分配候选订单的流程继续保留。

  • 第一阶段仅 A，界面可显示唯一选项；以后增加多个账号不改变批次归属结构。
  • 读取与确认入库分别防重复：领取核对条件更新是否成功，回写匹配批次账号和本次凭证。
  • 候选匹配依据实际成交账号，不能用同商品其他用户的最新任务。已有订单按成交事实查重，来源矛盾提示冲突，不静默覆盖。
  • 未来若增加“多个账号一起导入”，服务端按账号拆独立子批次，分别进度／错误并统一展示；多个 profile 不领取同一子批次。
  • 离线账号的新导入读取不得伪报执行成功；提示目标账号状态，批次恢复仍按自身账号与领取规则。

3.2 公共拍卖历史与个人查询

“每件商品只对应 A 或 B”的旧前提已经失效。个人入札、最终出价与提交图表看自己的归属；公共 Yahoo 拍卖历史仍按商品保存一份，不因三个用户参与就读取三遍。

已实现采集选择落札商品优先使用实际成交账号；未落札商品从参与该商品的在线账号按稳定顺序选择一个。读取失败且明确未取得结果时，可以在后续重试选择其他有读取权限的相关账号；不并行读取同一商品。账号切换不能把三次失败上限变成“每账号三次”。

成功历史、过期提示及既有字段不覆盖；历史读取账号变更写入诊断。不同账号可见内容是否一致须在真实页面验收中确认，账号私有内容不能当公共数据展示。当前按此方式适配多人参与，真实页面权限差异仍需核对。

3.3 商品与成交模型边界

products 保存公共商品信息；tasks 保存各用户意图与执行账号；商品账号归属保存名额；orders 保存实际成交与后续流程。同一商品可以有多用户任务及多账号入札记录，只有真正落札的归属产生订单。商品当前价可共享，用户最高价、自己是否领先及验证状态独立。

本计划默认沿用当前单件商品成交范围及订单唯一保护。开发审计必须检查按 product_id 查订单并覆盖的入口，不能把其他账号订单更新成当前用户。Yahoo 多件数量拍卖／多个独立成交若需支持，另行设计成交标识、订单唯一约束与表格查重，本次不直接删除现有保护或宣称已支持。

4.2 防抢任务与防重复执行

  1. 提交即预留：检查候选在线与商品位置，原子预留并建立任务；数据库唯一／条件更新保护最后一个位置，两个并发提交只能一个成功。定时任务接受后同样占位。
  2. 先分配，再领取：插件只获取自身账号工作；未知绑定、身份不匹配和重复实例不领取。PIN 状态不能被合并成禁止提交标志。
  3. 领取必须成功：条件更新只有一方成功；响应丢失后通过稳定请求标识恢复领取，不猜测结果或另领任务。
  4. 操作前再次核对：副作用步骤前检查任务、归属和领取有效；实例失联后停止后续操作。
  5. 回写不可越权：心跳、status、touch、快照与 BID_RESULT 均核对账号及本次领取；迟到结果不改变新执行。
  6. 转交原子完成：确认当前账号停止且无有效／未知入札，预留下一个符合条件的商品账号位置、作废旧领取并更新原任务。名额被并发占用则重新检查后续候选，不抢其他用户。
  7. 未知结果先核实：超时／重启不能仅因 60 秒无心跳就重放未知副作用；核对入札／落札事实，必要时等待核实。
不能仅凭数据库锁承诺 Yahoo 操作绝对只发生一次

领取凭证能阻止旧数据库回写，但无法撤销已发给 Yahoo 的请求。实际防护必须包括操作前核验、实例停止、结果核实及未知结果不自动重放，付款和消息发送同样适用。

4.3 生命周期与隔离

  • 同用户后续提交保持已有商品归属，转交后不重新默认落回主账号、不额外占一个名额。
  • 尚未出价且确认无有效入札，或被明确黑名单拒绝且无有效旧入札时，可以按规则安全释放原位置；被超过、系统取消或结果未知不能立即释放。保留历史以便真实落札追溯。
  • 只有现有 A 时没有可转交备用，失败沿用适用的单账号处理；不生成等待不存在或离线备用的新任务。
  • 角色／顺序调整不改绑存量任务与订单，新增账号不自动复活已终止任务；停用新分配不应直接丢弃已有订单工作。
  • 同商品多个用户分别结束自己的任务。一个用户落札不能直接把其他账号未知结果当作已核实失败；先核对实际结束与 Yahoo 状态。
  • 窗口与 tab 使用账号＋实例上下文，插件只清理自身页面；同标题窗口操作要准确定位。
  • 各账号恢复自身批次和验证；过期领取作废，邮箱刷新／提交结果未知时等待新点击，不自动重放。
  • 公共商品快照避免旧同步回退最新价格／结束时间；先区分完整同步、失败和空结果，再按账号更新记录。自动延长时间仍按实际 Yahoo 页面核实。

1A · 审计与基线列出全部全局运行 key、插件接口、旧领取／回写入口、账号相关字段；记录当前待办、各 flag 和统计口径。先设计迁移 dry-run。能够说明每个 key 是共享配置、账号状态还是公共采集；形成准确文件清单与回退方案。
1B · A 身份与存量数据注册唯一 A；核实后映射存量空账号记录，合法非空值不覆盖；建立账号列表、商品＋账号归属、运行状态及协议结构。profile 显式绑定 A。迁移幂等，任务／订单行数与关联不变；不重建任务、重付或重导入。无真实备用账号、无转交。
1C · 领取与同步按账号分配／领取／心跳／回写／快照全链路携带 A；入札、落札与订单匹配按账号；followup、消息、导入、历史领取继承账号；补未知结果恢复保护。A正常执行；错误账号、重复实例与迟到结果被拒绝。单账号商品归属不丢失，个人统计与基线一致。
1D · 工作状态与验证交易／扫描／付款／收货请求及完成 slot 迁到 A；提醒和验证按账号保存；系统输入统一锁。共享配置一份，在线状态与 PIN 状态分开判断。scan计数和待办不中断；继续／关闭只作用于 A，PIN不阻断提交；未知支付／验证码动作不自动重放。
1E · 界面与单账号发布账号管理显示 A，列表式数据结构；flag、任务、订单和提醒显示执行账号。完成只读统计对比、离线拒绝新分配检查，并同步部署 API、两端静态与 A 插件。通过单账号验收，观察完整工作周期；原策略和订单行为回归，最新离线／PIN规则单独验收，稳定后进入阶段二。

阶段一的控制范围

  • 只启用 A，备用业务分配与自动转交保持关闭。一个商品可分配名额仍只有 A，所以其他用户同商品仍被拒绝；拒绝原因是没有第二名额，不能把旧全局单用户限制写死在新结构里。
  • 账号状态采用集合结构，不硬编码 A/B、两个验证码或两组 flag；商品账号归属先用于 A，模拟多个账号验证结构，无需登录真实备用。
  • 不改用户表、税价与财务、出价策略、工作优先级；不同时删除三表冗余字段或重做截图／网络提速。
  • 配置与运行状态访问集中封装，逐步替换调用点；短期兼容有截止条件，不长期维护两套状态来源。
  • 旧协议兼容仅限唯一 A 的受控迁移期；正式账号化后禁止旧插件领取，接入备用前关闭默认猜 A 的入口。

阶段二 · 接入可配置的多个账号与 profile

结果：可增加、排序备用列表，逐个绑定独立 Yahoo／Gmail／profile，状态互不覆盖。先验证运行隔离，多人新分配与自动转交仍关闭。

  • 验证一个主账号＋两个以上备用账号的列表结构、身份检测、心跳与重复绑定拒绝，检查同一实际 Yahoo 不能占两个名额。
  • 各账号独立同步入札／落札、flag和扫描计数。备用有历史业务时先核实归属，不能套到 A 的用户。
  • 模拟混合账号订单、消息、导入和批次；账号选择、同捆隔离、付款未知保护须已具备，不能等备用真实落札后再补。
  • 验证多提醒分别处理、同标题窗口精准输入、全机前台排队；离线不被误报在线，PIN不被误报为禁止提交。
  • 验证统一配置为2时，各插件分别保持最多2个同时出价，3插件可合计6个；不存在服务器总出价并发池或按性能自动降速。停止新分配与已有业务处理分离，真实副作用按现有业务授权范围操作。

进入下一阶段：多账号读取与订单路由、验证、离线、实例冲突通过模拟验收，A 原流程持续正常。

阶段三 · 启用同商品多人分配，先不转交

结果：按在线账号及商品位置分配不同用户；主＋两个在线备用可接受三人，第四人失败。离线跳过，在线需 PIN 仍允许提交。

  • 移除全局“商品最新任务属于别人即拒绝”的限制，替换为商品＋账号名额事务分配；单条和批量共用入口。
  • 验证同用户不占第二名额、定时任务占位、最后名额并发竞争与请求去重；不同商品可以共用账号。
  • 批量按正式建任务预留账号，部分无名额只失败对应行；入队成功不承诺每件都已分配。
  • 调整入札列表、失败分析和落札匹配，防止同商品不同用户状态串写；保证只有实际成交归属产生订单。
  • 验证个人图表与统计不泄露其他用户最高价；后台区分任务数与去重商品数。先模拟，再小量验证。

进入下一阶段：三用户／第四人拒绝、不同商品共用账号、离线跳过、PIN允许及实际成交用户匹配验收通过。

阶段四 · 启用明确黑名单后的逐账号转交

结果：主账号或备用明确被卖家拉黑后，原任务继续向后找该商品可用账号；耗尽才终止，不抢其他用户、不循环。

  • 拆分黑名单方向，结构化错误码；原子预留后续位置、作废旧领取并更新原任务，记录固定账号 ID 与尝试轨迹。
  • 同商品占用和离线跳过，其他商品占用不影响转交，PIN不成为候选排除条件；全部不可用给出明确原因。
  • 有效入札、未知结果、已取消／已落札／已结束不得盲目转交；迟到回写与并发提交同时争名额须纳入事务测试。
  • 保留用户、最高价、策略、任务 ID 与原提交标识；转交不增加图表三角、活跃任务或批量提交失败提醒。
  • 测试备用1失败继续备用2、账号排序变化不重复尝试、取消不释放有效归属；通过模拟后小量业务验收。

范围：首次建议仅卖家明确拉黑触发自动转交。其他失败需单独定义证据；网络未知、PIN与价格上限不能一概当转交原因。

阶段五 · 多账号成交闭环与稳定发布

结果：任一账号落札后完整经历交易、消息、付款、发货、入表和收货，其他账号保持正常。

  • 验收同商品多人参与后的真实赢家／用户匹配、成交价、交易 URL 与税型；排序和角色调整不改订单归属。
  • 混合订单按账号分发，同捆不跨账号，验证和完成回写不清掉其他账号工作。
  • 验收公共历史选择、个人失败分析、90天统计、CSV、表格查重与修复／清理；用户最高价与账号私有内容隔离。
  • 补重启、离线、临近结束、并发窗口和多个账号验证场景；完成应用回归并记录真实页面验收，更新 AGENTS.md。

06验收与发布回退

6.1 第一阶段验收清单

  • 只启用 A，不需要新增或登录真实备用；账号结构和接口按列表设计，模拟其他账号验证拒绝越权。
  • 迁移前后任务／订单 ID、用户、金额、状态、URL、批次关联与已入表标识一致；重复迁移不重复写业务事实。
  • 单条／批量、定时／multi_bid、低价分步、税价与商品类型按原业务回归；A离线时新分配失败、A在线需 PIN 时提交成功。
  • 入札／落札同步、领先身份、订单用户归属、个人统计与单账号基线一致。
  • 交易、扫描、付款、消息、导入、收货及历史队列账号正确，flag／计数与恢复正确。
  • 邮箱、文字验证码、PIN 提醒与继续正常，迟到响应只处理对应账号当前事件；PIN不阻断提交。
  • 重启、响应丢失、超时恢复和重复实例不盲目重放出价、付款、消息或导入。
  • 同用户已有加价规则保留，其他用户同商品因仅有一个已占名额被拒绝。
  • 系统配置仍一个入口，账号状态独立，用户范围不泄露。

6.2 多账号分配、转交及订单验收

  • 主＋两个在线备用：同商品 user1／2／3分别分配，user4失败；最后位置并发提交只有一个成功。
  • 不同商品可以共用同一 Yahoo 账号，某账号处理其他商品不阻止当前商品的分配或转交。
  • 离线候选跳过，剩余全部离线直接提交失败，不建立等待恢复的新任务；在线需 PIN 的候选允许提交。
  • 同用户再入札、调价、followup不占第二账号；定时任务接受后占位；请求重试不重复建任务。
  • 批量入队与正式建任务分开反馈，无名额只失败对应行；已建任务转交不产生提交失败弹窗。
  • 入札记录按账号＋商品唯一，完整同步只清本账号；其他用户领先／仍在入札不覆盖自己的状态或失败分析。
  • 主账号黑名单转后续；备用1明确失败继续备用2；同商品其他用户占位和离线跳过，候选耗尽终止，不循环。
  • 转交与新提交并发争位不抢占；已尝试固定账号不因排序变化再次使用；迟到旧回写和重新领取拒绝。
  • 有效入札／取消／未知结果不立即释放名额或盲目转交，真实落札仍能追溯原用户。
  • 同商品多任务只给实际成交账号对应用户生成订单；后续全流程跟随该账号，同捆不跨账号、导入不猜全局最新任务。
  • 多账号flag、心跳、scan、验证、错误独立；同标题窗口不误输，处理一个提醒不清其他提醒。
  • 公共历史按商品一份，选择读取账号明确，换账号不重置三次失败上限；过期、迟到写入和清空保护保留。
  • 个人图表与统计用户隔离，后台区分任务／商品／成交数量；转交不增加任务／提交三角；表格不重复追加。
  • 新增／停用／排序不改存量归属，重复实际 Yahoo 身份拒绝，已终止任务不因新增账号自动复活。
  • 出价并发统一配置为2，三个插件各自最多2个，合计可同时运行6个；修改统一配置后各插件按原刷新机制应用同一新值。不得增加服务器总出价上限或自动性能调节，前台输入排队只限制对应焦点动作。

6.3 发布与回退建议

  1. 发布前：明确旧版基线；停止相关领取与写入，核实正在进行的 Yahoo 操作，停服务备份 SQLite。dry-run 输出字段／索引、行数、空账号分布、商品账号归属、待办与验证状态。
  2. 数据迁移：核实后将存量空账号归 A，非空有效 account_id 不覆盖；保留已支付、收货、入表、消息和队列事实，未知执行不强行重排。
  3. 协议切换：关闭旧插件领取，协调 API、静态与绑定 A 的新插件更新及 reload；第一阶段不启用真实备用。
  4. 分步放开：先 A 稳定，再账号列表与隔离，再同商品多人分配，最后安全转交；各阶段单独验收和记录。
  5. 发生异常：先停新分配／领取，保留诊断和 Yahoo 事实，按子步骤定位；不能只停掉已有待付款订单而丢弃事实。
  6. 回退：代码与数据回退分开。无外部写入才可直接恢复备份；已出价／付款／落札／入表后必须核对并保留新事实。多账号产生真实业务后不能简单回退到只认识 A 的旧程序。
